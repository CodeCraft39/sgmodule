# One device session to assess local playback processing

The production checkpoint is `7978e7b`. These tools are separate, temporary
instrumentation; the production request/response scripts are unchanged.
User-reported versions: YouTube 21.32.4, Quantumult X 1.8.1, Shadowrocket 2.2.93.
Record the iPadOS version in `session-notes.template.txt` before capture.

The goal is evidence for a fully local implementation, rather than another full
ad-blocking acceptance test. Nothing here implements local Onesie filtering.
No deployment or device test has been performed by the development tools.

## Before opening YouTube

1. Publish the checkpoint pair plus `tools/youtube-device/capture.js` to the
   existing CodeCraft39/sgmodule master paths. If using local scripts instead,
   substitute their local filenames in the supplied profiles. Refresh script
   resources in the selected client so the cached files are current.
2. Use one capture phase at a time. On QX, replace overlapping YouTube rewrite
   lines using the relevant `.conf` fragment and merge its MITM hosts into existing
   coverage. Do not replace unrelated rules/hosts. On Shadowrocket, use the
   relevant `.sgmodule` and disable the overlapping YouTube module. Both phases
   must keep the same custom caption/blocking arguments if you use any.
3. Enable the same HTTP capture/export method that produced the original handoff
   ZIPs. It must retain full request AND response bodies, headers, method, status,
   URL, and timestamps. An activity screenshot or script log cannot substitute
   for binary bodies. Check recording/export size limits; mark truncated records.
4. Keep the same YouTube account, network/proxy route, and test video across phases.
   A short session (one video for roughly 15–20 seconds per phase) is sufficient
   initially. Repeat these steps with the other proxy client afterward.

The raw HTTP captures and diagnostic export include session keys and potentially
account/session headers. Keep them private and send them as private attachments;
never commit them, paste them into an issue, or publish them at a script URL.
Only the helper code and sample profiles belong in the repository.

## Phase A — checkpoint Worker baseline

Select the matching profile:

- `quantumult-x.worker-baseline.conf`
- `shadowrocket.worker-baseline.sgmodule`

This retains the checkpoint's existing Worker handoff. It therefore uses
Maasea's service when the request key matches. There is no extra initplayback
response-body observer in this phase. Skip this phase and note that fact if you
prefer not to contact that service at all.

With this client active, force-quit YouTube and wait two seconds for old probe
work to finish. In **Safari on the iPad**, open:

`https://example.com/yt-local-capture/reset`

Expect JSON with `reset: true`. This resets only `YTLocalCapture.v1`, the helper's
own observations. It does not clear or alter YouTubeConfig or the ad cache.
The response is generated by the installed script; there is no remote export
server. A normal example.com page/404 means the export rule is not active.

Start a fresh recording, launch YouTube, and play the selected video for about
15–20 seconds. Record playback/ad/stall behavior and time to first picture.
Keep all relevant traffic, particularly:

- `youtubei/v1/config` and `youtubei/v1/log_event` requests/responses, if present.
- Complete Google `/initplayback?...ack...` transactions.
- Worker transactions to `init-stream.maasea.workers.dev`, if present. In a native
  URL replacement client the response may remain associated with the original
  Google URL; retain the whole transaction. QX's 307 and any follow-up request
  are separate evidence. A script log saying key-match is not proof of replay.

Force-quit YouTube, stop/save the recording, then open in iPad Safari:

`https://example.com/yt-local-capture/export`

Save the downloaded JSON as `qx-worker-baseline.json` or
`shadowrocket-worker-baseline.json`. Its observations can be empty in phase A;
its `currentConfiguration` snapshot is still useful. The captured Worker URL
also carries the key used for that handoff, so retain it privately.
Expected production log builds are `request-compat-20261101.1` and
`response-compat-20261101.1`. If phase A fails, record the failure and continue;
resolving the Worker transport is not a prerequisite for collecting phase B.

## Phase B — direct Google with observations

Replace phase A with:

- `quantumult-x.direct-google.conf`, or
- `shadowrocket.direct-google.sgmodule`.

This replaces the initplayback request handler with a pass-through observer.
The other API response filters and log_event key handling remain enabled.
The probe calls `$done({})` for playback traffic: it does not redirect, fetch,
change headers/body, or clear production keys. A response observer also records
metadata and capabilities for the actual response-script context.

Force-quit/reopen YouTube, start a separate recording, and play the same video
for about 15–20 seconds. Stop/save it and export the JSON again as
`qx-direct-google.json` or `shadowrocket-direct-google.json`. Do not reset between
phases A/B. Keep the complete config/log_event and Google initplayback transactions.

Look for `[YT-CAPTURE capture-20261101.1]` lines with both `role=request` and
`role=response`. Lines show lengths, binary representation, capability results,
and storage success. They do not print keys, bodies, authorization headers or
full URLs. There should be no checkpoint `YT-REQUEST ... endpoint=initplayback`
processing and no Worker handoff caused by the capture profile in this phase;
those indicate an old/overlapping request rule is still active.

**The response observer itself requires native body buffering.** The SR/Surge
profile requests a 2 MiB response ceiling. Surge documents pass-through above
that ceiling; Shadowrocket's native behavior still needs verification. QX's
effective limits on your build remain to be measured;
this profile does not claim to raise them. Do not infer a size limit from a
missing callback alone: inspect the native journal and exported transaction.

If playback stalls only in phase B, retain that evidence. Then disable just its
`yt.capture.response` line (Shadowrocket) or the initplayback
`script-response-body` line (QX), keep the direct request observer, and retry
once with a separate capture. This distinguishes the body-observer path from
ordinary direct playback. Request-side key snapshots remain available. Do not
change the API response rule, log_event rule, or body/header values for this retry.

Ads or ad-free playback in either phase do not establish successful local
Onesie filtering. That processing has not yet been implemented.

## What to send back

For each proxy client, provide the two private export JSON files and complete
HTTP exports for phases A/B where its recorder supports them. If Shadowrocket
cannot export binary bodies, send its JSON/notes and say so; do not transcribe
binary data or spend time finding a new capture tool. The minimum starting
input is one complete direct-Google QX request/response with matching keys. Include the one extra observer-disabled capture
only if needed. Bundle with a completed copy of `session-notes.template.txt`.
If a key is missing or recording is truncated, note it; do not manually edit
YouTubeConfig to force a match. The complete config/log_event bodies can supply
additional evidence. Keep encrypted bodies intact; do not convert them to text.

The private JSON contains up to 32 recent observations and selected session-key
snapshots. It does not contain raw HTTP bodies, which must come from the native
capture export. Request keys are sampled before asynchronous capability checks.
Shared preference writes are best effort; compare native session IDs/timestamps
and report `stored=false` or missing observations. The latest configuration is
also included at export time and may differ from an earlier request's snapshot.

## Capability results and their limits

The helper uses public test vectors for AES-128-CTR and HMAC-SHA256; it never
uses session keys for these tests. It tests
native gzip/Brotli stream round trips on a tiny fixed payload, access to the
secure-random API, an empty WebAssembly module, and text-encoder API presence.
The random check verifies a successful API call, not entropy quality. The WASM
check instantiates an empty module; it is not proof that a particular Brotli
module will fit or perform adequately. Asynchronous capability work
has a 1.2-second total deadline and is reused for up to ten minutes separately
for request and response contexts. It performs no network requests.

- `pass`: the small native operation succeeded in this script context.
- `unsupported`: compression stream constructors rejected that format name.
- `unavailable`: necessary APIs were absent.
- `failed`: an available operation threw or produced an unexpected result.
- `timeout`: the operation did not finish before the probe deadline.
- `not-run`: a safe timed test could not be started.

Neither `pass` nor failure establishes throughput or full local feasibility.
These checks cover the standard Web APIs used by the helper; they do not
enumerate every app-specific native extension. Missing standard features can
potentially be supplied by bundled implementations.
We still need the actual Onesie stream and matching keys to verify framing,
authentication, decompression, filtering, reconstruction, and device performance.
No large synthetic memory/CPU stress test runs on the device.

The exporter uses the clients' documented synthetic response shapes:
[QX example](https://github.com/crossutility/Quantumult-X/blob/master/sample-echo-response.js)
and [Surge request-script API](https://manual.nssurge.com/scripting/http-request.html).
Native loading and export behavior remain device-test candidates; Node mocks
cannot validate the app configuration parser or iPad networking engine.

## Cleanup after capture

While the diagnostic export rule is still enabled, open its reset URL again and
confirm `reset: true` to clear private helper snapshots. Then restore the normal
YouTube rules, remove the export/reset rules, and remove temporary MITM additions
(example.com and the Worker host if added solely for capture). Preserve unrelated
rules and hosts. Production YouTubeConfig remains intact.

The earlier `youtube.response.qx.js` experiment is still pending its agreed
post-validation cleanup; it is not used by these profiles.

## Development verification

The helper builds independently of the production response runtime. With Node
22.21.1, TypeScript 5.9.3 and esbuild 0.25.12 prepared exclusively in /private/tmp:

```sh
python3 tools/youtube-device/profiles.py --check
python3 tools/youtube-device/check.py \
  --node /private/tmp/maasea-refactor/node/node-v22.21.1-darwin-arm64/bin/node \
  --typescript /private/tmp/maasea-refactor/typescript/package/lib/tsc.js \
  --esbuild /private/tmp/maasea-refactor/esbuild/package/bin/esbuild \
  --work-dir /private/tmp/maasea-refactor/device-check
```

The checker verifies strict typing, deterministic output, generated profiles,
Node VM behavior, public crypto vectors, timeouts, native-API absence/failures,
private export boundaries, storage isolation, and unchanged production files
relative to the checkpoint. Exact results are recorded in validation.json.
Remove all downloaded tools and intermediate outputs after development. No global
installation, node_modules directory, or persistent environment change is needed.
